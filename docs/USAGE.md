# 日常使用与问题排查

尚未安装插件时先看 [安装与接入](INSTALL.md)。

## 打开与关闭

从 Ubuntu 应用菜单搜索 **SessionGlow**，或执行：

```bash
# Debian 软件包安装
sessionglow

# 源码安装
~/Workspace/SessionGlow/run.sh
```

- 拖动标题栏：移动面板，松开后保存位置。
- 右上角 `−`：隐藏面板，后台继续接收状态。
- 右上角 `···`：打开菜单。
- 点击托盘图标：显示/隐藏面板。
- 菜单“退出 SessionGlow”：关闭整个程序。
- 前台终端运行时，Ctrl+C 也可退出。

退出面板不会中断 OpenCode。再次打开后，插件通常在约 5 秒内重连；历史摘要会先从本地缓存恢复。

## 五股电流与四种状态

| 状态 | 灯管表现 | 含义 |
| --- | --- | --- |
| 蓝色 · 进行中 | 五股粗细不同、相互交叉的电流，沿线粒子和空腔粒子平缓移动 | 正在处理任务，或正在自动重试 |
| 红色 · 任务失败 | 电流收成轻微抖动的直线，粒子停住 | 任务终止失败；主动取消会附带“已取消” |
| 绿色 · 已完成 | 绿色液体充满空腔并舒缓流动，没有电流和粒子 | 任务已结束 |
| 黄色 · 待确认 | 五股电流保持波幅，电流与漂浮粒子更明显地抖动 | 有权限请求或问题需要你在 OpenCode 中回应 |

每根蓝色、黄色灯管包含 19 颗沿电流移动的粒子和 38 颗空腔粒子。状态切换经过约 0.8 秒过渡；中途再次切换会从当前画面继续，不重新生成粒子位置。

灰色待机表示缺少可靠的任务结果。连接中断时会保留并调暗上次状态，同时显示断线文字。断线不是任务完成，普通工具报错也不一定表示整个任务失败。

灯管只负责提示，确认或授权操作仍在 OpenCode / OpenChamber 中完成。

## 哪些会话会显示

默认显示最近发起任务的 **5 个主会话**，可调整为 1–12 个。

- 按用户最近发起任务的时间排序。工具活动、心跳和完成事件不改变顺序。
- 子 Agent 会话不单独占行；它们的活动与确认请求归入所属主会话。
- 主任务仍运行时，某个子任务完成不会使灯管提前变绿。
- 完成和失败的会话会保留，直到有更新的会话将其挤出列表。
- 多个 OpenCode 服务和终端的会话汇总展示；同一 session ID 只显示一次。
- 每行下方显示项目名，鼠标悬停可看完整标题、路径和会话 ID。

如果某个旧会话不在前五个，可以增大会话数量，或在该会话中发起一个新任务。只是点击浏览历史，不算发起任务。

插件初次连接会回填当前项目最近最多 32 个会话、每个会话最近 12 条消息的元数据。实时任务不等待历史回填；很长的老会话如果最后一次用户消息超出这段历史，首次恢复的排序可能不完整，此后的新任务会准确记录。

## 设置外观

菜单“显示会话数”提供快捷选项；“外观设置”可调整：

| 设置 | 范围 | 默认值 |
| --- | --- | --- |
| 会话数量 | 1–12 | 5 |
| 动画帧率 | 10–60 | 30 |
| 面板不透明度 | 65%–100% | 97% |
| 动效强度 | 20%–120% | 85% |

设置立即生效并保存到 `~/.config/sessionglow/config.json`。菜单“始终置顶”可开关置顶行为；窗口位置也会保存。

降低帧率可以减少绘制负载，降低动效强度可以减少画面干扰。也可以暂时隐藏面板：隐藏后停止绘图，状态接收继续运行。

## 演示与预览

```bash
# 软件包安装者用 sessionglow 替换下面的 ~/Workspace/SessionGlow/run.sh
# 预览全部状态，第五根灯管每 5 秒切换一次
~/Workspace/SessionGlow/run.sh --demo

# 演示 15 秒后自动退出
~/Workspace/SessionGlow/run.sh --demo --quit-after 15

# 导出合成预览图，不捕获用户桌面
~/Workspace/SessionGlow/run.sh --render /tmp/sessionglow.png
```

演示窗口明确标注“演示数据”，不会改变真实会话或写配置。真实窗口和演示窗口可同时存在；记得从对应窗口的菜单退出演示。

## 排查：终端会话可见，OpenChamber 会话不可见

1. 查看真正运行的服务：

   ```bash
   pgrep -af 'opencode.*serve'
   openchamber status
   ```

2. 查看面板实际接入的来源：

   ```bash
   curl -s http://127.0.0.1:8790/health | /usr/bin/python3 -m json.tool
   ```

3. 比较 `sources[].endpoint`。OpenChamber 可能使用动态端口，与你手动启动的 4096 是两个不同进程；不要只根据命令窗口猜测。
4. 如果插件是在服务启动后安装或更新的，等待任务结束后完整重启正确的服务。自动管理模式可用 `openchamber restart --port 3000`；外部服务则重启对应 `opencode serve`。
5. 在 OpenChamber 中打开对应项目或会话，触发该项目的插件初始化，再检查 `sources[].directory` 和 `session_count`。
6. 若来源已连接但行未显示，确认该会话是主会话，并在最近 N 个任务之内。必要时增大显示数量。

`connections` 统计的是项目插件实例，不是 OpenCode 服务数。一个 OpenChamber 后台初始化很多项目时，出现十几个连接是正常的。

2026-09-17 在本机排查时，OpenChamber 实际使用自己的动态端口，期间观察到 **39195**、重启后的 **34767** 等地址，并曾缓存旧 WindowRag 插件。另开的 **4096** 服务独立存在。两种来源都已通过真实本地任务的蓝色→绿色验证。动态端口以后仍可能变化，以 `/health` 为准。

## 其他常见问题

**`/health` 提示连接失败**：面板没有运行、启动失败，或使用了另一个 `--port`。先从终端执行 `run.sh` 查看错误。

**8790 端口占用**：先检查是否已有面板，使用已有托盘入口。若端口确被其他程序使用，按安装文档同时修改面板端口和 `SESSIONGLOW_PORT`。

**访问 4096 返回 401**：这是 OpenCode 服务自身的认证要求，不代表 SessionGlow 插件出错。面板自己的诊断接口是 8790。OpenChamber 与外部服务的认证配置必须一致。

**插件入口存在，但没有来源**：确认服务运行用户相同，且没有用 `opencode --pure` 或 `OPENCODE_PURE=1` 禁用外部插件。容器、其他用户及其他配置目录需要在实际服务环境中安装。

**来源字段没有地址/PID**：通常是仍在运行的旧版插件，重启对应服务后会补齐。当前正在使用的其他终端也可能尚未重启。

**修改插件后刷新项目仍无效**：OpenCode 进程可能保留模块缓存。完整重启服务；`/instance/dispose` 不能保证重新加载文件内容。

**黄色一直不消失**：检查主会话及其子会话是否还有其他未回答问题或授权请求。多个确认请求必须全部处理。

**面板显示“连接中断”**：插件超过约 20 秒没有发送心跳。检查对应 OpenCode 服务是否退出，以及面板接收端口是否一致。

## 本地文件

| 路径 | 内容 |
| --- | --- |
| `~/.config/sessionglow/config.json` | 面板设置与位置 |
| `~/.local/state/sessionglow/sessions.json` | 最多 512 个会话摘要 |
| `~/.config/opencode/plugins/sessionglow.js` | 插件安装入口 |
| `~/.local/share/applications/sessionglow.desktop` | 应用菜单入口 |

软件包提供的系统启动项位于 `/usr/share/applications/sessionglow.desktop`，运行文件位于 `/usr/share/sessionglow`。配置 `XDG_CONFIG_HOME` 时，插件入口位于该目录的 `opencode/plugins/sessionglow.js`。升级和卸载的区别见 [安装文档](INSTALL.md)。

插件发送标题、项目路径、会话/父会话 ID、状态和时间等元数据，以及用于排查的服务地址与 PID。不会向面板传输提示词正文、回答正文、工具参数或服务密码。
